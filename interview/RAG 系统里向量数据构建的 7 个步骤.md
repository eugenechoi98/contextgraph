RAG 系统里向量数据构建的 7 个步骤（口播版）
“如果面试官问我：‘在 RAG 系统里，向量数据到底是怎么构建的？’。我是这么看的。

首先，我们要纠正一个底层的误区：向量数据库里存的绝对不是整篇大文档，而是通过精细拆分、向量化之后的一条条片段数据。 如果在面试里一开口只说‘把文档扔进向量数据库让模型去查’，那就太像一个只做过 Demo 的初学者了。在企业真实的生产级别项目中，向量数据的构建其实有一套非常严谨的 7 步工程流程。

第一步：文档采集。 这是整个工程的起点。你需要明确企业内部知识的来源，是 PDF、Word、Excel，还是网页、合同条款或者系统接口的文档？在企业项目里，数据源通常非常复杂，有的是本地上传，有的是从数据库定时同步，有的是通过 API 拉取或网页爬取。我们第一步要解决的就是数据来源的稳定性与可更新性。

第二步：文档解析。 采集来的文档不能直接丢给大模型，因为不同格式的文档里包含着大量非结构化干扰。比如 PDF 里会有页眉页脚、目录、页码和各种水印甚至扫描图片；Word 里有各种标号、表格；网页里有广告和导航信息。这一步的核心目标，就是把所有格式各异的资料，统一转译成大模型能够理解的、结构化的可读文本。

第三步：文本清洗。 解析完的文本往往有很多脏数据。我们需要通过代码进行深度清洗，去除无意义的内容（如多余空格、异常换行、重复的页眉页脚和乱码）；同时，这里还涉及业务时效性的冲突处理。比如同一个制度，知识库里同时存在 2022 版和 2026 版，我们就必须通过清洗和规则去重、去旧，防止大模型把淘汰的旧规则也捡回来。因为在真实工程里，Garbage in, Garbage out（输入的是垃圾，输出的也必然是垃圾），清洗决定了知识库的基本质量。

第四步：文本切分（Chunking）。 这是 RAG 里最核心的一步。大模型和 Embedding 模型都有输入长度限制，而且用户的提问通常很具体，系统需要检索出最精准的片段，而不是整本书。我们会把文章切成一段段的 Chunk。切分非常讲究工程经验：最简单的是固定长度切分（比如每 500 字切一段），但这很容易把完整的句子拦腰切断，导致语义丢失。所以更好的方式是按结构切分，比如按照标题、段落、章节的业务边界来切。同时，为了防止上下文断裂，我们通常会引入 Overlap（重叠窗口）。比如设定 Chunk 大小为 500 字，Overlap 设定为 100 字，这样相邻的两个 Chunk 之间就会有 100 字的语义重叠，确保大模型能看到完整的上下文，避免答错。

第五步：Embedding 向量化。 这一步把切好、清洗好的每一个文本 Chunk，通过 Embedding 模型编码成一串高维度的数字数学向量（根据模型不同，可能是几百维到上千维）。这就像把文字标在了‘语义空间’的坐标系里，两个句子的意思越接近，它们在空间里的距离就越近。在做企业化落地时，Embedding 模型的选择极为关键，必须根据行业和语言（比如是中文知识库，还是涉及金融、医疗、法律等专业术语场景）来进行精准的选型或微调，它直接决定了检索的召回效果。

第六步：元数据绑定（Metadata）。 很多人以为向量数据库只存向量，其实这是初学者的误区。在真实工程里，每一条向量数据都必须严格绑定它的 Metadata（元数据）。一条完整的向量数据，应该包含：Chunk ID、原始文本内容、对应的向量、以及它属于哪个文件、第几章、第几页、甚至它的上传时间、版本号以及权限控制标签。有了 Metadata，系统才能实现答案溯源（告诉用户这句话出自哪份文档的第几页），并进行精准的权限隔离（比如老板能查全部制度，普通员工只能检索自己部门的内容）。

第七步：写入向量数据库并建立索引。 向量生成并绑定完元数据后，最后一步就是正式写入向量数据库（如 Milvus、Qdrant、Pinecone 等）。写入完成后，数据库必须建立向量索引（如 HNSW、IVF_PQ 等）。因为在高维空间里，如果每次查询都去跟几百万、上千万条向量挨个计算距离，系统延迟会直接崩溃。通过索引结构，可以实现高维向量的近似最近邻搜索（ANN），在极短的时间内快速召回最相关的片段。

把这七个步骤在面试里完完整整地讲清楚，面试官立刻就能明白，你不仅懂概念，而且对 RAG 的底层工程链路有着非常扎实的全局掌控力。”

🎙️ 视频二：大模型 RAG 检索优化与生产落地痛点（口播版）
“在明确了向量数据如何构建之后，我们就要看用户提问时，整个 RAG 系统在生产环境里到底是怎么检索并运行的。

当用户输入一个问题时，整个链路是倒过来的：系统首先把用户的问题送进同一个 Embedding 模型转换成向量，然后去向量数据库里进行检索，找出语义距离最近的 TopK 个 Chunk。接着，结合 Metadata 进行权限和时效性过滤。有些高阶系统还会通过 Reranker（重排模型） 进行二次精细化打分，把真正最贴合问题的前几条片段筛选出来。最后，把这些召回的文本片段拼接进 Prompt，交给大模型去生成最终的答案。这就是 RAG 的核心思想：先检索，再生成。

但是，为什么很多企业的 RAG 系统上线后效果却不好？在真实落地中，我们会遇到很多非常致命的工程难点和痛点，这也是评判一个系统是 Demo 级别还是生产级别的关键。

第一个痛点就是‘原始文档质量差和解析崩溃’。 比如合同表格、图片或者 PDF 里的复杂排版，传统的文本提取工具一扫，整个表格的行列结构、标题层级就全乱了。如果标题和段落的关系倒置，切分出来的 Chunk 就会变成一堆毫无逻辑的文字碎片，大模型读了只能胡说八道。

解决方案：必须在第二步解析时引入多模态解析或专门处理表格的解析工具，尽可能在文本化时保留文档的原始物理结构（如段落、表格列表等），为后面的合理切分打好基础。

第二个痛点就是‘Chunk 切分不合理导致的语义断裂’。 比如一份 35 页的差旅报销流程，里面包含好几条平行的业务规则。如果切分时切得太碎，或者完全没有设置 Overlap 重叠窗口，就很容易把一条长规则或者一个连续的业务逻辑硬生生切断，导致前后文的意思完全对不上，模型吃到了残缺的上下文，自然就会给出错误的回答。

解决方案：不能盲目用固定长度切，而是要根据业务类型（如技术文档按标题切、合同按条款切），并且严格根据大模型上下文窗口和业务特征，动态调优 chunk_size 和 chunk_overlap 两个核心参数。

第三个痛点就是‘纯向量检索在特定业务场景下的无能为力’。 向量检索擅长处理‘意思相近’的模糊泛化，但它对精确匹配非常迟钝。比如用户直接问：‘差旅报销制度三章四条的内容是什么？’或者‘某某型号产品的代号是多少？’。这时候大模型如果只靠向量检索，可能召回了一堆提到‘差旅’或‘产品’的无关片段，根本抓不准那条精确的条款。

解决方案：大厂在真实生产里绝对不只用向量检索，而是标配 混合检索（Hybrid Search），也就是‘向量检索 + 关键词检索（如 BM25）+ Reranker重排’。向量检索负责兜底语义相似的内容，关键词检索负责精准抓取特定的条款、编号和产品名，两路并发检索出来之后，再通过 Reranker 模型进行精细化的相关度重排。这样既能召回语义相关的长文本，又能确保特定精确问题能把标准答案顶到最前面。

所以在面试里，如果只说‘把文档变向量塞进数据库’，那这个说法太像 Demo 了。在真实的工业界，我们必须把混合检索、智能切分、元数据控制和 Reranker 组合起来，把 RAG 变成一套可控的工程学，这才是解决大模型知识库落地痛点的唯一解法。”
